# Проектирование IBus-границ и SQLite-хранилища

## Цель этапа

Создать минимальный Rust-каркас GooseSwitcher и рабочее пользовательское
SQLite-хранилище. Этап определяет границы будущих компонентов, но не реализует
распознавание текста, обработку клавиш, подключение к IBus или графический
интерфейс.

## Границы

В этап входят:

- единый Cargo-пакет с библиотекой;
- отдельные модули для IBus, конфигурации, хранилища, пользовательских правил,
  распознавания и приложения настроек;
- определение типов пользовательских правил и публичного API хранилища;
- определение стандартного XDG-пути базы;
- инициализация и версионирование схемы SQLite;
- CRUD настроек и пользовательских правил;
- unit-тесты создания базы и CRUD правил.

В этап не входят:

- зависимость от IBus, обработка событий клавиатуры или глобальный перехват;
- преобразование раскладки, токенизация и словарное распознавание;
- зависимость от GTK4/libadwaita и полноценный UI;
- системные словари, контекстная или частотная модель;
- systemd unit, RPM и установочные файлы.

Такое ограничение сохраняет совместимость с Wayland: будущая обработка ввода
остаётся внутри IBus, а глобальный перехват не появляется даже как заготовка.

## Архитектура пакета

Пакет предоставляет библиотеку со следующими публичными модулями:

- `ibus` — документированная граница будущего адаптера IBus;
- `config` — типы ключей и значений конфигурации;
- `storage` — разрешение пути, подключение SQLite, миграции и CRUD;
- `rules` — модель пользовательского правила и его действия;
- `recognition` — документированная граница будущего движка распознавания;
- `settings_ui` — документированная граница будущего GTK-приложения.

На этом этапе модули `ibus`, `recognition` и `settings_ui` не получают
исполняемой логики или внешних зависимостей. Их назначение — сделать владение
ответственностью явным, не проектируя преждевременно API ещё не реализованных
подсистем.

Хранилище представлено конкретным типом `SqliteStore`. Trait для backend не
вводится: в MVP требуется только SQLite, а узкий конкретный API проще и не
мешает извлечь trait позже, когда появится второй потребитель или backend.

## Расположение базы

Основной путь:

```text
$XDG_DATA_HOME/gooseswitcher/gooseswitcher.db
```

Если `XDG_DATA_HOME` не задан, используется:

```text
$HOME/.local/share/gooseswitcher/gooseswitcher.db
```

Настройки и словарные правила являются переносимыми пользовательскими данными,
поэтому база относится к XDG data, а не cache, runtime или state. При открытии
стандартного пути родительский каталог создаётся автоматически. API также
принимает явный путь, чтобы тесты не изменяли окружение процесса и не затрагивали
пользовательские данные.

Если невозможно определить домашний каталог или создать каталог, открытие
возвращает типизированную ошибку.

## Модель данных

### Настройки

`Setting` содержит строковые `key` и `value`. Значения остаются строковыми на
границе хранилища: интерпретация конкретных настроек принадлежит модулю
`config`, а схема не требует миграции при добавлении нового ключа.

Таблица:

```sql
CREATE TABLE settings (
    key        TEXT PRIMARY KEY NOT NULL,
    value      TEXT NOT NULL,
    updated_at INTEGER NOT NULL
);
```

### Пользовательские правила

`RuleAction` имеет ровно три варианта:

- `ConsiderCorrect` (`consider_correct` в SQLite);
- `NeverCorrect` (`never_correct`);
- `AlwaysReplace` (`always_replace`).

`UserRule` содержит идентификатор, исходный токен, действие, необязательную
замену и временные метки. Исходный токен уникален: для одного написания
действует ровно одно пользовательское правило. Создание или обновление по
исходному токену обеспечивает приоритет последнего явно заданного правила.

`replacement` обязателен и не может быть пустым для `AlwaysReplace`; для двух
остальных действий он должен отсутствовать. Это проверяется типом/конструктором
до SQL и ограничением `CHECK` в базе.

Таблица:

```sql
CREATE TABLE user_rules (
    id          INTEGER PRIMARY KEY,
    source      TEXT NOT NULL UNIQUE,
    action      TEXT NOT NULL CHECK (
        action IN ('consider_correct', 'never_correct', 'always_replace')
    ),
    replacement TEXT,
    created_at  INTEGER NOT NULL,
    updated_at  INTEGER NOT NULL,
    CHECK (
        (action = 'always_replace' AND replacement IS NOT NULL
            AND length(replacement) > 0)
        OR
        (action <> 'always_replace' AND replacement IS NULL)
    )
);
```

Метки времени хранятся как Unix seconds UTC. Это не привязывает схему к
формату даты или часовому поясу.

## Миграции

Первая версия схемы применяется в транзакции. Версия хранится в
`PRAGMA user_version`:

1. новое подключение с версией `0` получает таблицы и версию `1`;
2. подключение с версией `1` открывается без повторной миграции;
3. версия выше поддерживаемой возвращает ошибку вместо потенциально опасного
   открытия новой схемы старым приложением.

Список миграций хранится рядом с реализацией хранилища как встроенный SQL.
Отдельный migration framework не добавляется: для одной локальной базы он не
оправдывает новую зависимость.

## Публичный API хранилища

`SqliteStore` предоставляет:

```rust
pub fn open_default() -> Result<Self, StorageError>;
pub fn open(path: impl AsRef<Path>) -> Result<Self, StorageError>;

pub fn get_setting(&self, key: &str) -> Result<Option<Setting>, StorageError>;
pub fn set_setting(&mut self, key: &str, value: &str) -> Result<(), StorageError>;
pub fn delete_setting(&mut self, key: &str) -> Result<bool, StorageError>;

pub fn upsert_rule(&mut self, rule: NewUserRule)
    -> Result<UserRule, StorageError>;
pub fn get_rule(&self, source: &str)
    -> Result<Option<UserRule>, StorageError>;
pub fn list_rules(&self) -> Result<Vec<UserRule>, StorageError>;
pub fn delete_rule(&mut self, source: &str) -> Result<bool, StorageError>;
```

`list_rules` возвращает стабильный порядок по `source`. `upsert_rule` сохраняет
`created_at` существующего правила, обновляет остальные изменяемые поля и
`updated_at`, затем возвращает фактическую запись из базы.

`StorageError` различает ошибки определения XDG-пути, файловой системы,
SQLite, неподдерживаемой версии схемы, повреждённого значения действия и
недопустимого правила. Ошибки не скрываются за строковым типом.

## Зависимости

- `rusqlite` — SQLite API без ORM и migration framework;
- `directories` — корректное разрешение XDG data-каталога на Linux;
- `tempfile` только как dev-dependency для изолированных тестов файловой базы.

IBus, GTK4 и libadwaita намеренно не добавляются, пока соответствующие
интеграции не реализуются. Настройки `rusqlite` должны позволять сборке Fedora
использовать системную SQLite, не встраивая приватную копию библиотеки.

## Проверка

Unit-тесты используют настоящую SQLite-базу во временном каталоге без mock:

- открытие нового пути создаёт файл, обе таблицы и `user_version = 1`;
- повторное открытие сохраняет данные;
- настройка записывается, читается, обновляется и удаляется;
- каждый вариант пользовательского правила создаётся и читается;
- upsert сохраняет идентификатор и `created_at`, но изменяет действие;
- список правил имеет стабильный порядок;
- удаление существующего и отсутствующего правила различается;
- недопустимое сочетание действия и замены отвергается до записи.

Перед завершением выполняются `cargo fmt --check`, `cargo test` и
`cargo clippy --all-targets --all-features -- -D warnings`.
